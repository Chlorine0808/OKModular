# 構造 IO: ブロックの配置そのものを 1 つの入出力として扱う

レシピは、単体のブロックではなく**配置全体**を要求したり生成したりできます。配置は
**パターン**として 1 度だけ書き、名前でいくつのレシピからでも参照します。

パターンのファイルは `config/okmodular/structure_io/` に置きます（`recipes/` や `structures/`
と同じ階層）。ディレクトリ名は設定値です（`modular.cfg` の `structureIoDirectory`）。

> [!NOTE]
> `symbol` の入出力（[JSON フォーマット §3.2](../recipes/JSON_FORMAT.md#32-ブロックsymbol)）が
> 数えるのは**個数**です — 「その記号のどこかに 3 個」。パターンが訊いているのは別の質問で、
> 「**この形が、この向きで、このブロックのところに**あるか」です。

## 1. ファイル構造

1 ファイルに、パターン 1 個・配列・`patterns` 配列を持つオブジェクトのいずれでも書けます。

```json
{
  "patterns": [
    {
      "name": "altar_core",
      "anchor": "Q",
      "mappings": {
        "S": "minecraft:stone",
        "G": "minecraft:gold_block:0"
      },
      "layers": [
        [ "SSS",
          "SQS",
          "SSS" ],
        [ "G G",
          "   ",
          "G G" ]
      ]
    }
  ]
}
```

## 2. プロパティ

| プロパティ | 型 | 説明 |
| :--- | :--- | :--- |
| `name` | String | レシピから参照する識別子（必須・重複不可） |
| `layers` | Array | 形状。構造体定義と同じ書き方（必須） |
| `mappings` | Object | 文字 → ブロック ID。**ブロック ID 文字列のみ**で、構造体定義が受けるオブジェクト形式・複数候補形式は使えません |
| `anchor` | String | レシピが名指ししたブロックに重なるセルを示す 1 文字。既定は `Q` |

`layers` は行文字列の配列でも `{ "rows": [...] }` でも書けます（構造体定義と同じ 2 通り）。

### 予約文字

| 記号 | 意味 |
| :--- | :--- |
| （空白） | パターンに含まれない。検査も設置もしない |
| `_` | 空気。input では「空気であること」、output では「空気にする」 |
| アンカー | `mappings` に無ければ**印だけ**で、そのセルには手を付けない |

それ以外の文字は `mappings` に**必ず**エントリが要ります。無い文字があるとファイルは
読み込まれず `structures/errors.txt` に出ます。黙って落とすと、**見た目より少ない数の
ブロックしか検査しないパターン**ができてしまうからです。

### アンカー

レシピは機械側の構造体の記号を名指しします。その記号として記録された各ブロックが候補になり、
**アンカーのセルがそのブロックに重なるように**パターンが置かれます。

パターンの中にアンカーを描けるので、3×3×3 の配置を台座の**中心に**合わせられます
（隅を基準にする必要がありません）。`anchor` も `Q` も書かなければ、パターンの最初のセルが
基準になります。

`anchor` に書いた文字が `layers` に無い場合、隅を基準に読み替えたりせず**エラーになります**。

### 向き

**パターンは自分の `defaultFacing` を持ちません。** 変換に使うのは**使われる側の機械の向き**なので、
機械と一緒に回り、機械に対してだけ回転することがありません。

裏を返すと、同じファイルでも縦置きの機械と横向きの機械では意味が変わります（縦置きでは層が行に
移ります）。**その機械の構造体を書くときと同じ向きで**書いてください。

### 機械の外へ伸ばす

パターンは形成判定が触るブロックに限定されません。機械の形の外に出るセルも普通に解決するので、
IO の領域を機械の横や下に置けます。

## 3. レシピからの参照

```json
{
  "inputs": [
    { "type": "structure", "pattern": "altar_core", "symbol": "P", "consume": true }
  ],
  "outputs": [
    { "type": "structure", "pattern": "altar_spent", "symbol": "P" }
  ]
}
```

| キー | 意味 |
| :--- | :--- |
| `pattern` | パターンの `name` |
| `symbol` | パターンの基準になるブロックの記号 |
| `amount` | 一致・書き込みを要求するアンカーの数。既定は 1。式が使える |
| `consume` | input のみ。一致した配置を丸ごと消す |
| `optional` | 一致しなくてもレシピを開始・完了できる |
| `index` | 指定した割り当て番号のポートだけを対象にする |
| `pertick` | 稼働中も検査 / 書き込みを繰り返す |

### 入力として

アンカーが 1 つと数えられるのは、**すべてのセルが一致したときだけ**です。部分一致は部分点に
なりません。そこが、ブロック入力を並べたものとの違いです。

`consume` は個数ではなく**配置全体**を消します。半分だけ残った配置は「小さい配置」ではなく
壊れた配置で、次の検査でも一致しません。

### 出力として

空気のセルも含めて**すべてのセルを書き込みます**。同じ仕組みで、配置を作ることも
（空気で描いて）消すこともできます。

**上書きします。** セルごとの「置けるときだけ」判定はありません。パターンは一体として置くもので、
埋まっているセルを飛ばすと、**レシピが約束した配置ではないもの**を機械が作ったことになります。
特定の地面の上でだけ動かしたいなら、前段に `structure` の入力を置いてください。

容量チェックが見るのは**アンカーが足りているか**です。記号が 1 つも無いレシピは、入力を消費して
何も置かないのではなく、開始そのものを断ります。

## 4. スキーマのバージョン管理

パターンのファイルは読み込み時に構造マイグレーション機構を通ります。後からフォーマットを変えても
既存のファイルを自動で直せます。変換されたファイルは書き戻され、元のファイルは `.bak` として残ります。

これがパターンをレシピ JSON に埋め込まず別ファイルにしている理由です。レシピ JSON には
スキーマの版管理が無いので、そこに書いたものは永久に固定されます。

## 5. コマンド

- `/okmodular reload`: 構造体・パターン・Tier・レシピを再読み込みします。レシピはパターンを
  名前で解決するので、**パターンのほうが先に**読み直されます。
